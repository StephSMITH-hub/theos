## Overview & Purpose

This guide documents the complete, end-to-end pipeline for transforming raw AI-generated sermon transcripts from the Two Kinds of Righteousness teaching series into professionally formatted Markdown documents. The teaching series is organized hierarchically:

Series → Part → Track → (Chunk)

- Series: A major thematic arc (e.g., Series 2, Series 3, Series 4)
- Part: A sub-division within a series (e.g., Series 3, Part 5)
- Track: A single recorded teaching session/sermon within a Part (typically 20–30 tracks per Part)
- Chunk: A processing sub-unit created by splitting a Track for manageable formatting (typically 3–8 chunks per Track, ~2,000–2,500 words each)
[!IMPORTANT] The governing principle of this pipeline is the REFINED CLAUDE STANDARD VERBATIM PRESERVATION. Verbatim means preserving 100% of the speaker's original vocabulary, theological terminology, doctrinal definitions, and authentic teaching voice, while actively smoothing spoken syntax into clear, readable written prose. Where oral speech contains false starts, fragmented thoughts, or spoken run-ons, restructure them into coherent, grammatically sound sentences. Furthermore, where conversational speech vacillates between changing pronouns ('we', 'you', 'they'), standardize and harmonize them into consistent third-person pronouns (e.g., 'the believer', 'one', 'they') to ensure a continuous, authoritative, and unified flow of thought.

## Source Material: What You Start With

### Raw Input Files

Each Track arrives as a .docx file generated by Fireflies AI, an automated transcription service. These files are named:

Two Kinds of Righteousness Series [X] Part [Y] Track [N].docx

Example:

Two Kinds of Righteousness Series 3 Part 5 Track 4.docx

### Characteristics of Fireflies AI Transcriptions

The raw transcripts have these consistent characteristics that the formatter must understand:

| Feature | Description |
| --- | --- |
| Wall of text | The entire sermon is rendered as continuous prose with minimal paragraph breaks |
| No headings | No structural organization whatsoever |
| No formatting | No bold, italic, or any typographic distinction |
| Speaker markers | Occasional Speaker 1: or name tags (inconsistent) |
| Timestamps | May include [00:00:00] style timestamps embedded inline |
| Fireflies footer | Typically ends with a watermark/footer like "Transcribed by Fireflies.ai" |
| Transcription artifacts | Occasional mishearings, run-on sentences, and phonetic approximations of Hebrew/Greek terms |
| Scripture mixed inline | Bible verses are not distinguished from the speaker's own words |
| Anecdotes mixed inline | Personal stories, side remarks, and audience interactions are blended into the expository text |


### Content Nature

The transcripts capture live sermon/teaching recordings where the speaker:

- Expounds on biblical texts with theological analysis
- Shares personal anecdotes and illustrations
- Interacts with the audience ("Is that clear?", "Are you following?")
- Reads scripture passages aloud
- Makes rhetorical remarks and side comments
- References Hebrew and Greek terms
- Cross-references multiple biblical passages

## Phase 1: DOCX → Plain Text Extraction

### Purpose

Extract the raw transcript text from the Fireflies .docx files into plain .txt files for processing.

### Method

Use Python's python-docx library to read the .docx and extract all paragraph text:

from docx import Document

def extract_text_from_docx(docx_path):
    doc = Document(docx_path)
    full_text = []
    for para in doc.paragraphs:
        text = para.text.strip()
        if text:
            full_text.append(text)
    return '\n\n'.join(full_text)

### Key Considerations

- Preserve everything — even seemingly garbled text, mishearings, or incomplete sentences. These are the speaker's actual words as transcribed.
- Strip Fireflies metadata — Remove any Fireflies watermark footer (e.g., "Transcribed by Fireflies.ai"), speaker labels like Speaker 1:, and embedded timestamps.
- Maintain paragraph boundaries — The original paragraph breaks from the .docx are preserved in the .txt output using double newlines (\n\n).
### Output

A single .txt file per track containing the full extracted text, ready for chunking.

## Phase 2: Chunking the Transcript

### Purpose

Split each Track's text into smaller, manageable chunks that can be individually processed by formatting subagents without exceeding context window or output limits.

### Chunk Size Target

| Parameter | Value |
| --- | --- |
| Target chunk size | ~2,000–2,500 words |
| Maximum chunk size | ~3,000 words |
| Minimum chunk size | ~500 words (final chunk of a track) |
| Chunks per Track | Typically 3–8, depending on Track length |


### Chunking Rules

- Split at paragraph boundaries — Never split mid-sentence or mid-paragraph. Always split between complete paragraphs (at \n\n boundaries).
- Aim for even distribution — If a Track has ~10,000 words and will produce 4 chunks, target ~2,500 words each rather than three chunks of 3,000 and one of 1,000.
- Respect topical coherence — Where possible, split at natural thematic transitions rather than purely by word count.
- Numbering — Chunks are numbered sequentially starting from c1.
### Chunking Implementation

def chunk_text(full_text, target_words=2400):
    paragraphs = full_text.split('\n\n')
    chunks = []
    current_chunk = []
    current_word_count = 0
    
    for para in paragraphs:
        para_words = len(para.split())
        if current_word_count + para_words > target_words and current_chunk:
            chunks.append('\n\n'.join(current_chunk))
            current_chunk = [para]
            current_word_count = para_words
        else:
            current_chunk.append(para)
            current_word_count += para_words
    
    if current_chunk:
        chunks.append('\n\n'.join(current_chunk))
    
    return chunks

### Output

Multiple .txt files per Track, saved in the Formatted/ subdirectory:

s3p5_t4_c3.txt
s3p5_t4_c4.txt
s3p5_t4_c5.txt

## Phase 3: Formatting to the Claude Standard

This is the core transformation step. Each raw .txt chunk is reformatted into a structured .md (Markdown) document following the Claude Standard — a specific, consistent formatting protocol.

### The Six Formatting Operations

Every chunk undergoes exactly six operations, applied in this order:

---

### Operation 1: Title Header (Chunk 1 of each Track only)

Rule: The first chunk of every Track receives a main title header at the very top of the file.

Format:

# Two Kinds of Righteousness — Series [X], Part [Y]: Track [N]

Example:

# Two Kinds of Righteousness — Series 3, Part 5: Track 4

Chunks 2+ of the same Track do NOT receive this title — they will later be appended below chunk 1 during assembly.

---

### Operation 2: Section Headings (`##`)

Rule: Insert descriptive ## level-2 headings at major thematic transition points throughout the text.

Guidelines for heading placement:

- Place a heading when the speaker shifts to a new topic, scripture passage, argument, or theological point
- Headings must stick strictly to the grammar and vocabulary of the speaker (derived directly from their exact words and thematic phrasing, never external generic or artificial academic formulations)
- Use Title Case
- Aim for approximately one heading every 400–600 words (3–6 headings per chunk)
- Never place a heading mid-sentence
Good heading examples:

## Covenant Renewal, God Doing It Again, and the Expectation of a New Exodus
## The Building Imagery of Creation: Analyzing "Banah", "Selah", and God's Dwelling Place
## Righteousness in Romans: Corporate Reconciliation vs. Individualistic Theology
## The Flood Narrative: God's Sorrow vs. Human Self-Destruction

Bad heading examples (too generic):

## Introduction          ← Too vague
## Bible Study           ← Too vague
## Discussion            ← Too vague
## Part 2                ← Not descriptive

---

### Operation 3: Scripture Block Quotes (`>`)

Rule: All scripture citations and direct Bible readings must be extracted from the flow of text and formatted as Markdown block quotes.

Format:

> **[Book Chapter:Verse]**
> [Full text of the scripture as the speaker read it]

Example — Before (raw):

Romans 15:4. Whatever things were written at four times written for our 
learning, that we through patience and comfort of the Scriptures may have 
hope. And I said that earlier that this is about textual reasoning...

Example — After (formatted):

> **Romans 15:4**
> Romans 15:4. Whatever things were written at four times written for our learning, that we through patience and comfort of the Scriptures may have hope.

And I said that earlier that this is about textual reasoning...

Key rules for scripture formatting:

- The bold reference line (> **Book Chapter:Verse**) is placed first
- The actual text the speaker read follows on the next blockquote line
- The speaker's commentary after the scripture resumes as normal paragraph text below the blockquote
- Preserve the speaker's exact words when reading the scripture — do NOT correct to a standard translation
- If the speaker reads multiple verses consecutively, they belong in a single blockquote
- If the speaker merely references a verse without reading it aloud (e.g., "as Paul says in Romans 5"), do NOT create a blockquote — leave it inline
---

### Operation 4: Italicization of Anecdotes and Side Remarks (`*...*`)

Rule: All personal anecdotes, illustrations, side remarks, audience interactions, rhetorical questions directed at the congregation, and conversational tangents must be wrapped in Markdown italics.

What to italicize:

| Category | Examples |
| --- | --- |
| Personal anecdotes | Stories about the speaker's own experiences, conversations with other pastors/teachers |
| Illustrations | Analogies, metaphors, and extended examples (e.g., sports analogies, cultural references) |
| Audience interactions | "Is that clear?", "Are you following?", "Who's following what I'm saying here?", "Huh?" |
| Rhetorical side comments | "You know", "Let me say something very quickly", "You know what I'm saying?" |
| Parenthetical asides | Brief tangential remarks that interrupt the main expository flow |
| Congregational responses | "Amen", "Yes sir", audience laughter references |


What NOT to italicize:

| Category | Reason |
| --- | --- |
| Scripture readings | These are block-quoted instead |
| Direct theological exposition | This is the main body text |
| Hebrew/Greek term explanations | These are part of the teaching content |
| Historical/scholarly references | These are substantive expository content |


Example — Before (raw):

So but in their minds it's a corporate one, which is still true. But they 
never foresaw, you know, this son of David...

Example — After (formatted):

So but in their minds it's a corporate one, which is still true. But they 
never foresaw, *you know,* this son of David...

Example of a longer anecdote:

Before:

And I did mention this one married teacher. The guy was upset about the 
interpretation of Genesis 2:18 and 19. Help me. And I said, let's just look 
at something. I said, forget about you, because that thing can destroy a 
whole industry.

After:

*And I did mention this one married teacher. The guy was upset about the 
interpretation of Genesis 2:18 and 19. Help me. And I said, let's just look 
at something. I said, forget about you, because that thing can destroy a 
whole industry.*

Italicization boundary rules:

- Short interjections (1–5 words) are italicized inline within the paragraph: ...text *you know* more text...
- Longer anecdotes (1+ sentences) are italicized as complete blocks: *entire anecdote paragraph*
- If an anecdote spans an entire paragraph, the whole paragraph is italicized
- If a paragraph mixes exposition and brief side remarks, only the side remarks are italicized inline
---

### Operation 5: Paragraph Structuring

Rule: Organize the text into continuous expository paragraphs with logical flow.

Guidelines:

- Maintain the original paragraph boundaries from the raw text as the baseline
- Do NOT break paragraphs into single sentences
- Do NOT merge all text into one enormous paragraph
- A paragraph should represent one coherent unit of thought (typically 3–10 sentences)
- Insert blank lines between paragraphs (standard Markdown)
- Each ## heading is preceded and followed by a blank line
---

### Operation 6: Footer Removal

Rule: Remove any Fireflies transcription watermark, footer, or metadata that appears at the end of the transcript.

Common footers to remove:

Transcribed by Fireflies.ai

Keywords: [list of auto-generated keywords]

Summary: [auto-generated summary]

[!CAUTION] Remove ONLY the machine-generated footer content. If the speaker's final words happen to be at the end of the file, they must be preserved.

## Phase 4: Verification of Integrity, Flow & Consistency

### Purpose

Confirm that the formatted output faithfully preserves all of the speaker's theological vocabulary, doctrinal concepts, and core teaching, while ensuring that disjointed oral syntax is smoothed into clear, readable written prose, shifting pronouns are stabilized into third person, and all subheadings stick strictly to the speaker's own grammar.

### Verification Method

After formatting, perform the core verification checks:

def verify_refined_formatting(raw_text, formatted_text):
    # 1. Vocabulary Preservation: All doctrinal words, Greek/Hebrew terms, and scriptures are present.
    # 2. Readability & Structure: Spoken false starts and fragmented thoughts are smoothed into coherent prose.
    # 3. Pronoun Consistency: Conversational 'we/you' drift harmonized into third person ('the believer', 'one', 'they').
    # 4. Subheadings: Headings (##) adhere strictly to the speaker's grammar and vocabulary.
    # 5. Formatting Markers: Scripture passages blockquoted (>), anecdotes/side remarks italicized (*...*).
    return True

### Acceptance Criteria

| Metric | Requirement |
| --- | --- |
| Vocabulary & Doctrine | 100% preservation of the speaker's theological terms, scriptures, and teachings |
| Sentence Structure | Oral false starts, run-ons, and fragments smoothed into clear, readable written prose |
| Pronoun Consistency | Conversational pronoun shifts harmonized into consistent third-person references |
| Subheadings / Summaries | Strictly forged from the speaker's own grammar, phrases, and vocabulary |
| Scriptures & Anecdotes | Scriptures blockquoted with bold citations; personal stories/remarks italicized |


### Common Verification Failures

| Issue | Cause | Fix |
| --- | --- | --- |
| Spoken run-on or false start | Natural speech hesitation or repetition | Restructure into clean, readable written sentences preserving meaning |
| Inconsistent pronoun shift | Speaker drifting between 'we', 'you', 'they' | Harmonize into third-person pronouns ('the believer', 'one', 'they') |
| Subheading too generic or academic | External phrasing introduced | Derive heading directly from speaker's exact words and grammar |
| Omission of core teaching or scripture | Accidental skipping during formatting | Restore full exposition and complete scripture blockquote |
| Unitalicized personal anecdote | Missed personal story or congregation remark | Wrap anecdote or rhetorical interaction in *italics* |

## Phase 5: Assembly — Merging Chunks into Complete Tracks

### Purpose

Combine all formatted chunks of a Track into a single, complete formatted document.

### Assembly Procedure

- Order chunks sequentially: c1, c2, c3, ... cN
- Concatenate with section continuity: The # Title from chunk 1 becomes the document title. Chunks 2+ are appended below with their ## headings maintaining a logical flow.
- Review transitions: Ensure that the junction between chunks reads naturally — no duplicate headings, no abrupt breaks.
### Assembly Script

def assemble_track(formatted_dir, series, part, track_num):
    import os
    
    prefix = f"s{series}p{part}_t{track_num}_"
    chunks = sorted([
        f for f in os.listdir(formatted_dir) 
        if f.startswith(prefix) and f.endswith('_fmt.md')
    ])
    
    assembled = []
    for chunk_file in chunks:
        with open(os.path.join(formatted_dir, chunk_file), 'r', encoding='utf-8') as f:
            content = f.read().strip()
            assembled.append(content)
    
    return '\n\n---\n\n'.join(assembled)  # Optional: use --- as chunk separator

### Output

A single merged Markdown file per Track, or conversion to .docx for the final deliverable.

## Phase 6: Final Output & Cleanup

### Final Deliverable Format

The completed formatted Tracks are saved as .docx files in the Formatted/ subdirectory:

Two Kinds of Righteousness Series [X] Part [Y] - Track [N]_Formatted.docx

### Cleanup Tasks

After all Tracks in a Part are fully formatted and assembled:

- Verify completeness: Every Track has a corresponding _Formatted.docx
- Delete intermediary .txt chunks: The s3p5_t4_c1.txt files are no longer needed
- Delete intermediary _fmt.md chunks: The s3p5_t4_c1_fmt.md files are no longer needed
- Delete raw .docx source files: Only if the user explicitly requests this
- Preserve the final `_Formatted.docx` files: These are the permanent output

## Subagent Orchestration Strategy

### Why Subagents?

Each Part contains 20–30 Tracks, each split into 3–8 chunks, yielding 100–200+ individual formatting tasks. Doing these sequentially would take many hours. Instead, the formatting is parallelized across multiple subagents.

### Batch Strategy

| Parameter | Value |
| --- | --- |
| Subagents per batch | 5–6 |
| Batches dispatched concurrently | 1–2 (to avoid rate limits) |
| Time between batch launches | Wait for at least 2–3 subagents from the previous batch to complete |
| Total batches per Part | Typically 20–30 |


### Subagent Task Template

Each subagent receives the following prompt:

Task: Format Chunk [M] of Track [N] (Series [X] Part [Y]) to the Refined Claude Standard.

Raw file: [full path to s3p5_tN_cM.txt]
Output file: [full path to s3p5_tN_cM_fmt.md]

Rules:
- PRESERVE THE SPEAKER'S VOCABULARY & GRAMMAR: Retain all doctrinal terms, unique phrasing, and concepts.
- SMOOTH SPOKEN SENTENCE STRUCTURE: Restructure oral false starts, run-ons, and fragmented thoughts into clear, readable written prose.
- THIRD-PERSON PRONOUN CONSISTENCY: Harmonize shifting conversational pronouns ('we', 'you') into consistent third-person perspective ('the believer', 'one', 'they').
- SUBHEADINGS MUST STICK TO SPEAKER'S GRAMMAR: Section headings (##) must use the speaker's own vocabulary and grammatical phrasing.
- SCRIPTURE CITATIONS: Format scripture readings into block quotes (>) with bold references (> **Book Chapter:Verse**).
- ITALICIZE ANECDOTES: Wrap all personal anecdotes, illustrations, audience questions, and side remarks in italics (*...*).
- [For Chunk 1 only: Add main title # [Series] — [Part]: Track [N]].

### Subagent Completion Tracking

Maintain a mental ledger of:

- Which chunks have been dispatched
- Which chunks have reported success
- Which chunks have failed (with error type)
- Which chunks need retry
### Monitoring Progress

After each batch completes, run a quick status check:

python -c "
import os
dir_path = r'[Formatted directory path]'
txt = set(f for f in os.listdir(dir_path) if f.endswith('.txt'))
fmt = set(f[:-7]+'.txt' for f in os.listdir(dir_path) if f.endswith('_fmt.md'))
missing = sorted(txt - fmt)
print(f'Total: {len(txt)}, Done: {len(fmt)}, Remaining: {len(missing)}')
print('Missing:', missing[:20])
"

## Error Recovery & Retry Protocol

### Common Error Types

| Error | Cause | Recovery |
| --- | --- | --- |
| RESOURCE_EXHAUSTED (429) | API rate limit or quota exceeded | Wait 5–10 minutes, then retry in smaller batches |
| proto: unexpected EOF | Network interruption or server restart | Immediately retry — the task was not started |
| model unreachable | Temporary API outage | Wait 2–3 minutes, then retry |
| Individual quota reached | Daily/weekly usage cap hit | Wait for quota reset, or switch to a different model |
| Server restart notification | System-wide restart killed all subagents | Check which chunks completed before restart, then resume only the missing ones |


### Retry Protocol

- Identify failures: Parse system messages for error notifications
- Check disk for completed files: A subagent may have written the file before crashing — check if _fmt.md exists
- Retry only truly missing files: Re-run the progress check command above
- Reduce batch size: If quota errors are frequent, reduce from 6 subagents per batch to 3–4
- Add delays: Space batch launches further apart
### After a Server Restart

- Run the progress check to see current state (how many .txt vs _fmt.md)
- Get the list of all missing files
- Resume dispatching from where things left off
- Do NOT re-dispatch already-completed chunks

## The Claude Standard — Exhaustive Rule Reference

### Summary Card

┌──────────────────────────────────────────────────────────┐
│              REFINED CLAUDE STANDARD                     │
│                                                          │
│  1. # Title (Chunk 1 only)                               │
│  2. ## Section Headings (Sticks to Speaker's Grammar)    │
│  3. > Scripture Block Quotes (with **bold reference**)   │
│  4. *Italicized anecdotes and side remarks*              │
│  5. Continuous expository paragraphs                     │
│  6. Sentence Structure Smoothed (Readable Written Flow)  │
│  7. Third-Person Pronoun Consistency Harmonized          │

│  9. Fireflies footer removed                             │
│                                                          │
└──────────────────────────────────────────────────────────┘

### Decision Tree for Formatting

flowchart TD
    A[Read a sentence from the raw text] --> B{Is it a scripture reading?}
    B -->|Yes| C[Format as blockquote with bold reference]
    B -->|No| D{Is it a personal anecdote or side remark?}
    D -->|Yes| E[Wrap in italics *...*]
    D -->|No| F{Is it a topic transition point?}
    F -->|Yes| G[Insert ## Section Heading above]
    F -->|No| H[Keep as normal paragraph text]
    C --> I[Continue to next sentence]
    E --> I
    G --> H
    H --> I

### Hierarchy of Principles

- VOCABULARY & DOCTRINAL INTEGRITY — Preserve the speaker's authentic vocabulary, terms, and theological concepts without dilution.
- SYNTACTICAL READABILITY & FLOW — Fix spoken run-ons, false starts, and fragmented thoughts into smooth, elegant written prose.
- THIRD-PERSON PRONOUN HARMONIZATION — Maintain consistent third-person pronouns when the speaker drifts across conversational pronouns.
- SPEAKER-GRAMMAR SUBHEADINGS — Derive all section headings directly from the speaker's own vocabulary and phrases.
- Paragraph flow — Clean, readable paragraph structure.

## Checklist for Each Part

Use this checklist when processing a new Part:

### Pre-Processing

- ☐ Verify all raw .docx Track files are present in the Part directory
- ☐ Count total Tracks (typically 20–30)
- ☐ Create the Formatted/ subdirectory if it doesn't exist
### Phase 1 — Extraction

- ☐ Extract text from each .docx using python-docx
- ☐ Remove Fireflies footers and metadata
- ☐ Save as .txt in Formatted/
### Phase 2 — Chunking

- ☐ Split each Track's text into ~2,400-word chunks
